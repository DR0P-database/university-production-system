# Изменения в практических и лабораторных работах

Этот PR добавляет воспроизводимый учебный стенд для ПР №1–3 и ЛР №1–3 в каталоге `coursework/`. В собственном Compose-проекте лабораторные используют одну модель ПР №3, один API Gateway и три контейнера с отчётами. Существующие предметные микросервисы репозитория доступны по их прежней инструкции.

## Что добавлено по работам

| Работа | Изменения |
| --- | --- |
| ПР №1 | Compose с PostgreSQL, Redis, MongoDB, Neo4j и Elasticsearch. Проверяются доступность, расположение данных и журналы. Хост-порты выделены для учебного проекта и привязаны к loopback. |
| ПР №2 | Пять независимых CRUD-сценариев на синтетических данных. Скрипты обращаются к сервисам учебного Compose-проекта и очищают созданные ими учебные объекты. |
| ПР №3 | Единая реляционная модель с внешними ключами и недельным журналом, загрузчик четырёх специализированных проекций и проверка всех пяти хранилищ. Для ЛР №2 добавлено текстовое описание оборудования, для ЛР №3 — теги демонстрационных лекций. Обновление демо-набора сохраняет расписание и отметки. |
| ЛР №1 | Поиск слова и фразы в Elasticsearch, отбор завершённых лекций и участников в Neo4j, расчёт рейтинга в PostgreSQL и карточки топ-10 в Redis. Пропуск отмечается явным `false`; незаполненная отметка даёт `409`. |
| ЛР №2 | PostgreSQL отбирает курс по учебному году и семестру, MongoDB хранит требования к оборудованию, Neo4j считает активных слушателей по группам конкретного события. Совпадение темы, даты, времени, аудитории и преподавателя определяет совместное событие. |
| ЛР №3 | Neo4j определяет план для лекций с тегом специальной дисциплины выпускающей кафедры. PostgreSQL возвращает отметки завершённых занятий по недельным партициям, Redis — карточки студентов. За лекцию начисляются два академических часа. |

## Почему выбран этот вариант

В исходном проекте отдельные предметные сервисы владеют своими PostgreSQL-базами и проверяют междоменные ссылки через API. Учебный стенд формирует отчёты из одной реляционной модели с внешними ключами. Это позволяет сохранить прямую проверку ссылок и применить отдельные хранилища в тех частях запроса, для которых подходит их модель данных.

Из исходной ЛР №1 использована идея полнотекстового поиска фразы. Из ЛР №2 — отдельное текстовое описание технических требований и проверка соответствия семестра курсу обучения. Расчёт вместимости уточнён по расписанию, поскольку общий набор студентов специальности может быть больше состава отдельного занятия. Из ЛР №3 сохранены раздельные план и факт, исключение отмен и подсчёт подтверждённых посещений. Отчёт строится по курсам, назначенным группе. Сводка различий по каждому отчёту есть в [сопоставлении реализаций](1_lab/REPORT.md#сопоставление-с-проектом-коллеги).

JWT проверяется Gateway и сервисом отчёта. Swagger показывает вход и три операции чтения. Ключи и пароли генерируются при локальном запуске. [C4 и DFD](1_lab/ARCHITECTURE.md).

## Как проверить

1. Пройти развёртывание и проверки по инструкциям к [ПР №1](pr1/README.md) и [ПР №2](pr2/README.md).
2. Запустить лабораторный стенд по [инструкции](README.md) и выполнить `./pr3/check.sh`.
3. Войти в Swagger и выполнить три запроса с [контрольными параметрами](1_lab/README.md). На демонстрационных данных ожидаются 10 строк рейтинга, 8 событий вместимости и 156 строк по часам.
4. Запустить автоматические тесты из `coursework/1_lab/`:

   ```bash
   .venv/bin/python -m pip install -r requirements-dev.txt
   .venv/bin/python -m pytest -q
   ```

В отчёте описаны промежуточные результаты, сверка всех строк ЛР №2 и №3 с независимым SQL и ответы при отсутствующем JWT или незаполненных отметках. [Результаты](1_lab/REPORT.md).

Сборка PR проверена на чистом запуске. Пять сервисов ПР №1 прошли проверки доступности, пять CRUD-сценариев ПР №2 успешно завершились, проверка ПР №3 подтвердила согласованность проекций, а три отчёта вернули HTTP 200. Прошли 22 автоматических теста.
