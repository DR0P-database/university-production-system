# Лабораторная работа №2. Расчёт необходимой вместимости аудитории

## Цель и принятые правила

Я определяю необходимое количество мест для занятий выбранного курса заданного семестра и года обучения, у которых указаны технические требования. В ответе получаю полную карточку курса, полные карточки занятий и количество слушателей.

Под объёмом аудитории я понимаю вместимость в посадочных местах. Для расчёта площади в квадратных метрах данных о нормах площади нет. Семестр задаю по учебному плану от 1 до 12, год обучения — от 1 до 6. Дополнительно указываю год начала учебного года: это позволяет определить год набора по формуле `academic_year - study_year + 1`. Например, первый год обучения в 2026/2027 учебном году соответствует набору 2026 года. Семестры 1–2 относятся к первому году, 3–4 — ко второму и так далее.

В текущей модели нет индивидуального зачисления на курс. Поэтому я принимаю, что курс обязателен для всех активных студентов его специальности и выбранного набора. Это допущение, а не восстановленный факт индивидуального выбора. Исторический состав групп не хранится: расчёт использует текущее состояние. Для выборных дисциплин потребуется отдельная модель записи студентов на курс.

## Архитектура и выбор хранилищ

Я реализовал отдельный `room-report-service` в контейнере. Внешний запрос проходит через Gateway с JWT. Сервис обращается по HTTP только к academic-service и student-service, собственной базы не имеет. Gateway объединяет его OpenAPI с остальными методами.

PostgreSQL подходит для этого запроса: нужны точные фильтры по ID курса, специальности, семестру и году набора, а также по статусу студента. Я получаю полные карточки занятий вместе с полем `requirements`. Поскольку требования уже представлены коротким отдельным полем, MongoDB и Elasticsearch для этой выборки не нужны. При указании `equipment_term` выполняю регистронезависимый поиск подстроки именно в требованиях, а не морфологический полнотекстовый поиск. Непустое поле requirements считаю указанием технических требований; автоматически распознавать смысл произвольного текста система не умеет.

Количество мест рассчитываю по списочному составу активных студентов, а не по посещаемости. Пропуски предыдущих занятий не уменьшают требуемую вместимость. Расписание также не требуется: это планирование до назначения аудитории. Для каждого занятия предполагаю совместное проведение для всех подходящих групп. Если группы занимаются отдельно, результат является верхней оценкой; разделение на потоки пока не моделируется. Вместимости разных занятий не складываю: одна аудитория должна иметь максимум требуемых мест.

## Шаг 1. Запускаю систему и получаю JWT

Запускаю `docker compose up -d --build`. Для ЛР2 предусмотрен отдельный контейнер `room-report-service`, который доступен только во внутренней сети. Получаю токен через `POST /api/v1/auth/token` с development-учётной записью. Ответ — HTTP 200, тип токена bearer. Сам токен не публикую.

Затем вызываю `/api/v1/reports/capacity` без JWT. Получаю HTTP 401. После этого во всех запросах передаю `Authorization: Bearer <токен>`.

## Шаг 2. Подготавливаю воспроизводимый пример

В исходном наборе технические требования у проверенных занятий были пустыми. Поэтому я создал отдельный демонстрационный курс `LAB2-DEMO Технические средства обучения` для существующей специальности. Исходные курсы я не изменяю. В демонстрационном курсе есть три занятия: лекция с проектором, практика с компьютерами и лекция без требований. Третье занятие служит проверкой исключения из результата.

Подготовка выполняется через API владельца данных. Скрипт ищет демонстрационный курс по имени и занятия по порядковому номеру, поэтому повторный запуск на неизменённом наборе не создаёт копии.

## Шаг 6. Считаю слушателей

Для каждой группы отдельно получаю студентов через `/api/v1/students/students?group_id=...&status=active`. Обрабатываю все страницы. Таким способом я отдельно проверяю результат сервиса, который использует пакетный фильтр group_ids. Студентов объединяю по уникальному UUID.

Получаю **140 активных студентов**. Это ожидаемая вместимость для совместного занятия всех выбранных групп. Отчисленных, выпускников и студентов в академическом отпуске в число слушателей не включаю.

## Шаг 7. Получаю занятия и проверяю требования

Запрашиваю `/api/v1/academic/lectures?course_id=...`. Получаю 3 занятия. Оставляю только непустые requirements. Для практики технические средства также важны, поэтому lecture_type не ограничиваю только лекциями.

| Занятие | Тип | Требования | Слушателей | Мест |
|---|---|---|---:|---:|
| Презентация архитектурных решений | lecture | Проектор, экран, компьютер преподавателя | 140 | 140 |
| Практическое моделирование | practice | Компьютеры для каждого слушателя, доступ в Интернет | 140 | 140 |

Занятие «Обсуждение решений» не попадает в результат: requirements отсутствует. Получаю 2 подходящих занятия. Для каждого нужна аудитория минимум на **140 мест**, а не сумма вместимостей всех занятий.

## Шаг 9. Проверяю дополнительные сценарии

- С equipment_term=ПРОЕКТОР получаю одно занятие. Регистр запроса не влияет на поиск.
- С несуществующим оборудованием получаю HTTP 200 и пустой items; требуемая вместимость для отсутствующих подходящих занятий равна нулю, при этом общий состав слушателей остаётся в ответе.
- При study_year=2 и semester=1 получаю HTTP 422: параметры противоречат друг другу.
- При неизвестном UUID курса получаю HTTP 404.
- Без JWT получаю HTTP 401.

Модульный тест дополнительно проверяет обработку ошибки зависимости: HTTP 503 вместо частичного отчёта. Остановка живых зависимостей в этом прогоне не выполнялась.
