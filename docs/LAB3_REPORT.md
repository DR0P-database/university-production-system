# Практическая работа №3. Запланированные и посещённые часы по группе

## Цель и принятые правила

Я формирую отчёт по одной группе: для каждого её студента и каждого курса
специальности вывожу полные карточки группы, студента и курса, запланированные
и посещённые академические часы. Одно занятие по лекции равно двум академическим
часам. Практические и лабораторные занятия не учитываю.

«Необходимый объём запланированных часов» — это план, с которым сравнивается
посещение. Например, для группы назначено 10 подходящих лекционных занятий:
план каждого студента — 20 часов. Студент посетил 7 занятий — прослушал 14 часов.
План не уменьшается из-за пропусков. Это не количество оставшихся часов.

План беру из расписания группы, включая будущие занятия и исключая отменённые.
Занятия до даты зачисления студента исключаю. Посещение засчитываю только для
завершённых и уже закончившихся занятий с отметкой `is_present=true`.
Отсутствие отметки означает ноль посещённых часов.

## Отчёт по состоянию на дату

Параметр `as_of_date` задаётся в формате `ГГГГ-ММ-ДД`. Например:

```text
GET /api/v1/reports/group-lecture-hours
 group_id=05ba20c8-56f6-4350-bc6d-d3710b770773
 discipline_tag=специальная-дисциплина
 as_of_date=2026-09-07
```

Если дату не указать, используется сегодняшний день в часовом поясе отчёта
(по умолчанию Europe/Moscow). Дата и часовой пояс возвращаются в общей части
ответа: `as_of_date`, `timezone`.

- `planned_hours` — весь план по расписанию, в том числе после выбранной даты.
- `planned_hours_to_date` — сколько часов должно быть пройдено до конца
  выбранного дня включительно. Статус `completed` для этого показателя не нужен:
  назначенное, но не проведённое вовремя занятие остаётся в плане.
- `attended_hours` — сколько часов посещено к концу выбранного дня. Для
  сегодняшней и будущей даты учитываются только уже закончившиеся занятия
  к текущему моменту. Будущие посещения не прогнозируются.

Например, общий план предмета — 20 часов, к выбранной дате назначено 10,
студент посетил 8. Ответ: `planned_hours=20`, `planned_hours_to_date=10`,
`attended_hours=8`. Занятия выбранного дня входят в план независимо от времени
начала; для посещения занятие должно закончиться и иметь статус `completed`.

Это расчёт по датам занятий на текущих данных. Система не восстанавливает,
как выглядели расписание, состав группы или отметки в прошлом: исправленная
сегодня отметка за сентябрь изменит и сентябрьский отчёт.

## Что такое тег и какие данные генерируются

Тег — обычная текстовая метка занятия в поле `tags`. Он явно обозначает,
относится ли занятие к специальной дисциплине кафедры. Это не поиск слова в
конспекте и не требование к оборудованию. Например:

```json
{"title": "Основы архитектуры", "lecture_type": "lecture", "tags": ["специальная-дисциплина"]}
```

В генераторе у каждого SEED-курса шесть занятий:

| Номер занятия | Тип | Метка | Может попасть в отчёт |
|---|---|---|---|
| 1, 2 | lecture | специальная-дисциплина | Да, если назначено группе |
| 3 | lecture | общая-дисциплина | Нет, другой тег |
| 4, 5, 6 | practice | общая-дисциплина | Нет, это практика |

Параметр `discipline_tag=специальная-дисциплина` выбирает первые два вида
лекций. Совпадение тега точное, с учётом регистра. Генератор сам ставит метки
новым занятиям и добавляет их существующим SEED-занятиям при повторном запуске.
Карточки занятий и пользовательские теги сохраняются. Удалять базу не нужно.
За пределами демонстрационного набора метки задаются через POST/PATCH API лекций.
Система доверяет разметке: справочник тегов с отдельными связями кафедр пока
не моделируется.

## Архитектура и выбор хранилищ

Запрос проходит по цепочке пользователь → Gateway с JWT → отдельный контейнер
`group-hours-report-service` → academic-service, student-service,
schedule-service, attendance-service. Сервис отчёта не имеет своей БД и не
подключается к чужим базам напрямую. Gateway объединяет OpenAPI; метод находится
в группе `Лабораторная 3`.

Все необходимые данные структурированы и хранятся в PostgreSQL: группа,
студенты, курсы, метки лекций, расписание, отметки посещения. MongoDB и
Elasticsearch не нужны, поскольку поиск по содержанию материалов не выполняется.
Redis и обход Neo4j для расчёта тоже не требуются.

## Шаг 1. Пересобираю систему и обновляю генерацию

Из корня проекта выполняю:

```bash
docker compose up -d --build
docker compose run --rm --build seed-data
```

Первая команда добавляет контейнер отчёта, обновляет gateway и academic-service,
применяет миграцию `lectures.tags`. Вторая обновляет демонстрационный набор,
включая метки уже существующих SEED-лекций. Один только `up` генерацию не запускает.
Повторный запуск seeder также восстанавливает демонстрационные отметки
посещаемости — ручные изменения этих отметок проверяю после генерации.

## Шаг 2. Получаю JWT в Swagger

Открываю `http://localhost:8000/docs`. Выполняю `POST /api/v1/auth/token`:

```json
{"username": "api-user", "password": "api-password"}
```

Копирую `access_token`, нажимаю **Authorize**, вставляю токен и подтверждаю.
После этого защищённые методы доступны. Без токена метод отчёта должен вернуть 401.

## Шаг 3. Выбираю группу

Выполняю `GET /api/v1/students/groups` с `limit=100`. Нахожу группу
`SEED-U1-G01`, копирую её `id` и `specialty_id`. UUID зависит от текущей базы;
использую полученный UUID, а не пример из чужого запуска.

Далее вызываю `GET /api/v1/reports/group-lecture-hours`:

```text
group_id=<id выбранной группы>
discipline_tag=специальная-дисциплина
as_of_date=2026-09-07
```

Ожидаю HTTP 200. В `group` находится полная карточка выбранной группы.
В `items` — по одной строке на каждую пару «студент — курс»:

```text
student: полная карточка студента
course: полная карточка курса
planned_hours: полный план академических часов
planned_hours_to_date: план до выбранной даты включительно
attended_hours: посещённые часы к выбранной дате
```

Например, `planned_hours=4`, `attended_hours=2` означает: назначены две
подходящие лекции, студент посетил одну. Это поясняющий пример, не зафиксированный
результат запуска. Поля карточек не сокращаются до имени или UUID.

## Шаг 4. Руками восстанавливаю состав строк

1. Вызываю `GET /api/v1/students/groups/{group_id}`. Сравниваю карточку с `group` отчёта.
2. Вызываю `GET /api/v1/students/students` с `group_id` выбранной группы и `limit=100`.
   Выбираю одного студента; сохраняю его `id` и `enrollment_date`.
3. Вызываю `GET /api/v1/academic/courses` с `specialty_id` группы и `limit=100`.
   Выбираю курс и сохраняю его `id`.
4. В `items` отчёта нахожу строку с выбранными `student.id` и `course.id`.
   Сравниваю полные карточки с ответами API.

Если `total` превышает размер страницы, увеличиваю `offset` на число полученных
записей и продолжаю. Это относится ко всем спискам далее. В отчёте должны быть
все студенты группы × все курсы её специальности, включая строки с нулями.

## Шаг 5. Руками проверяю запланированные часы

1. Вызываю `GET /api/v1/academic/lectures` с `course_id` выбранного курса.
2. Оставляю карточки с `lecture_type=lecture` и меткой `специальная-дисциплина`
   в массиве `tags`. Записываю их ID.
3. Вызываю `GET /api/v1/schedule` с `group_id` выбранной группы.
4. Оставляю записи, у которых `lecture_id` входит в выбранные ID, статус
   не равен `cancelled`, а `scheduled_date` не раньше `enrollment_date` студента.
5. Считаю оставшиеся записи расписания и умножаю на 2 — это `planned_hours`.
6. Из них оставляю записи с `scheduled_date <= as_of_date` и умножаю их
   количество на 2 — это `planned_hours_to_date`.

Именно записи расписания определяют количество занятий. Одна лекция как
материал может быть проведена несколько раз — каждое проведение считается
отдельно. Будущее занятие тоже входит в план. Общие `lecture_hours` карточки
курса не беру: они могут включать лекции без нужной метки.

## Шаг 6. Руками проверяю посещённые часы

Для каждой записи расписания, оставшейся на шаге 5:

1. Проверяю `status=completed`, что дата занятия не позже `as_of_date` и
   дата/время окончания уже прошли по Москве.
2. Вызываю `GET /api/v1/attendance`, задаю `schedule_id` этой записи,
   `student_id` выбранного студента и `week_start_date` **из карточки расписания**.
3. Если есть отметка `is_present=true`, засчитываю 2 часа. Если отметки нет
   или `is_present=false`, засчитываю 0.
4. Складываю часы и сравниваю с `attended_hours` выбранной строки отчёта.

### Почему в посещаемости указан понедельник

`week_start_date` — дата начала недели, к которой относится занятие. Она нужна
для хранения отметок по недельным разделам таблицы БД. Это не дата посещения
и не дополнительное условие для студента.

Например, занятие в среду **09.09.2026** относится к неделе, начинающейся
в понедельник **07.09.2026**. Поэтому:

```text
scheduled_date = 2026-09-09  — когда было занятие
week_start_date = 2026-09-07 — к какой неделе оно относится
is_present = true          — студент присутствовал на занятии 9 сентября
```

При ручной проверке просто копирую `week_start_date` из расписания в запрос
посещаемости. При вызове самого отчёта указываю группу, тег и при необходимости дату — недели
он определяет сам. Проверка совпадения недель защищает от ошибочно связанной
отметки; несогласованные данные дают 503 вместо недостоверного результата.

## Шаг 7. Проверяю исключения

- Вызываю отчёт с `discipline_tag=несуществующий-тег`: строки студентов и курсов
  сохраняются, но все часы равны нулю.
- Смотрю занятие №3 курса: это лекция, но с другой меткой; в плане её быть не должно.
- Смотрю занятия №4–6: это практика; в лекционные часы они не входят.
- Проверяю студента с `is_present=false`: соответствующее занятие входит в план,
  но не добавляет посещённых часов.
- Передаю тег из одних пробелов: ожидаю 422. Неизвестный UUID группы даёт 404.

Генератор создаёт отметки только для первого занятия каждой недели. Для других
занятий отсутствие отметок ожидаемо и даёт 0 посещённых часов; это не означает,
что эти занятия исключаются из плана.

## Шаг 8. Сохраняю результаты и сравниваю автоматически

```bash
python tools/lab3/capture.py
```

Скрипт получает JWT, выбирает первую SEED-группу по имени, читает исходные
карточки и отметки через Gateway, отдельно считает часы и сравнивает каждую
строку с итоговым отчётом. Предметные данные не изменяет. Дополнительно проверяет
401 без токена, 422 для пустого тега и нулевые часы для несуществующего тега.
Если генератор ещё не добавил теги, скрипт завершается с понятной ошибкой.

Для конкретной группы:

```bash
python tools/lab3/capture.py --group-id <UUID>
python tools/lab3/capture.py --as-of-date 2026-09-07
```

При успехе выводит `OK`, группу, число студентов, курсов, строк и несколько
результатов. Полные промежуточные ответы, список включённых/исключённых занятий,
независимый расчёт и итоговый ответ сохраняются в `docs/lab3/evidence.json`.
При передаче даты журнал сохраняется отдельно, например
`docs/lab3/evidence-2026-09-07.json`. Токен в журнал не записывается. UUID и цифры беру из этого файла после запуска.

## Вывод и ограничения

Отчёт сопоставляет план и фактическое посещение по специальным лекциям для
каждой пары «студент — курс». Используется текущий состав группы, включая все
статусы студентов; история переводов не восстанавливается. Все курсы
специальности считаются курсами группы: индивидуальный выбор дисциплин
не моделируется. Полный план берётся из всего доступного расписания группы,
план и посещение к дате ограничиваются параметром `as_of_date`. Каждый запрос к сервисам читает их
текущее состояние, общего транзакционного снимка между сервисами нет.
