# Лабораторная работа №1. Отчёт о выполнении и проверке запроса

## Цель работы

В этой работе я получаю десять студентов с минимальным процентом посещения лекций, в содержании которых встречается заданный термин или фраза. Для каждого студента вывожу его полную публичную карточку, группу, процент посещения, количество посещённых и подходящих занятий. Период и поисковый термин указываются в общей части отчёта.

## Условия выполнения

Я выполняю проверку на запущенной системе через API Gateway по адресу `http://localhost:8000`. Контейнеры предварительно собраны командой `docker compose up -d --build`. Я использую существующий демонстрационный набор и не изменяю его во время проверки.

Время фиксации результатов (UTC): `2026-11-04T10:14:22.637914+00:00`.

Полный журнал запросов и ответов сохранён в [evidence.json](evidence.json). Токен в журнале скрыт. В тексте ниже я привожу реальные результаты этого запуска. UUID относятся к текущей базе и при пересоздании данных могут измениться.

## Почему я использую эти хранилища

Поиск по тексту я выполняю через academic-service, который обращается к Elasticsearch. Его анализатор приводит слова к нижнему регистру и использует русский стеммер. Это позволяет искать словоформы, а не только точное совпадение символов. В режиме `words` должны совпасть все токены одного документа, а в режиме `phrase` учитывается их последовательность. В индекс входят аннотации лекций и тексты материалов; сами материалы хранятся в MongoDB.

После поиска я получаю структурированные данные через сервисы, владеющие PostgreSQL-базами: academic-service, schedule-service, student-service и attendance-service. Отметки посещаемости выбираются с ограничением недель, что соответствует ключу партиционирования. Redis и Neo4j в вычислении этого отчёта напрямую не нужны: обход графа и поиск по номеру зачётки здесь не выполняются.

Сервис отчётов не подключается к чужим базам. Запрос проходит по цепочке пользователь → Gateway с проверкой JWT → report-service → сервисы данных. C4-модель находится в `docs/C4.dsl`, DFD — в `docs/DFD.puml`.

## Шаг 1. Получаю доступ к API

Сначала отправляю `POST /api/v1/auth/token` с development-учётной записью `api-user`. Получаю HTTP 200 и Bearer-токен. Затем проверяю тот же защищённый метод отчёта без токена: сервер возвращает HTTP 401. Следовательно, анонимный клиент не может получить отчёт. В дальнейших запросах передаю заголовок `Authorization: Bearer <токен>`.

## Шаг 2. Задаю условия отчёта

Я выбираю термин `нормализация`, режим `words` и период с 1 сентября по 31 октября 2026 года включительно. Фильтры кафедры, специальности, группы и курса не задаю, поэтому проверяю все подходящие группы.

```text
term=нормализация
search_mode=words
date_from=2026-09-01
date_to=2026-10-31
```

## Шаг 3. Нахожу лекции по содержимому

Отправляю `GET /api/v1/academic/search/lectures` с `q=нормализация`, `search_mode=words`, `limit=100`. Собираю уникальные ID лекций. Если ответ содержит `next_cursor`, выполняю следующий запрос с этим курсором, пока курсор не станет пустым. Это важно: совпадения могут находиться в нескольких материалах одной лекции, но сама лекция не должна дублироваться.

В результате получаю **16 уникальных ID**. Далее запрашиваю карточки через `/api/v1/academic/lectures`, передаю повторяющийся параметр `ids` и фильтр `lecture_type=lecture`. После фильтра остаётся **16 лекций**. Практические занятия в расчёт не включаю.


## Шаг 4. Получаю проведённые занятия

Запрашиваю `/api/v1/schedule`: передаю найденные ID через повторяющийся параметр `lecture_ids`, статус `completed` и границы периода. Различаю лекцию как учебный материал и занятие как конкретное проведение лекции для группы. Для процента посещения нужны именно занятия расписания.

Получаю **68 занятий для 34 групп**. По всем страницам забираю полный результат, а не только первые сто записей. Период полностью предшествует дате прогона, поэтому будущих занятий в нём нет.


## Шаг 5. Получаю группы и студентов

По `group_id` из расписания запрашиваю `/api/v1/students/groups`, затем `/api/v1/students/students` с повторяющимся параметром `group_ids`. Для списков использую `limit=100` и увеличиваю `offset`, пока не получу количество записей, указанное в `total`.

Я получаю **34 групп и 1000 студентов**. Здесь принципиально не ограничивать список десятью студентами: сначала нужно рассчитать посещаемость всех кандидатов.


## Шаг 6. Получаю отметки посещаемости

Запрашиваю `/api/v1/attendance`, передавая ID занятий в `schedule_ids`. Для выбранного периода задаю `week_from=2026-08-31` и `week_to=2026-10-26`: это понедельники недель, содержащих начало и конец периода. Ограничение по фактическим датам уже применено к расписанию.

Для этих конкретных занятий получаю **0 отметок**. Это существенный результат проверки: в текущем наборе подходящие лекции есть, но отметок для них нет. Согласно принятому правилу отсутствие отметки считается пропуском. Я не подменяю эти данные придуманными посещениями.


## Шаг 7. Отдельно рассчитываю ожидаемый результат

Для каждого студента беру занятия его группы не раньше даты зачисления. Считаю число подходящих занятий и количество отметок `is_present=true`. Использую формулу:

```text
процент посещения = 100 × посещённые занятия / подходящие занятия
```

Если подходящих занятий нет, студента не включаю в рейтинг: делить на ноль нельзя. Сначала сортирую по точному отношению посещений к занятиям, затем по UUID студента для устойчивого порядка при равенстве. После сортировки беру первые десять записей и округляю процент до двух знаков.

В расчёте участвует **1000 студентов**. Отдельный расчёт выполняется скриптом по промежуточным ответам API, без вызова внутренней функции расчёта report-service.

## Шаг 9. Дополнительно проверяю поведение метода

Я повторяю запрос с термином `несуществующийтерминлабораторная`. Сервер возвращает HTTP 200 и пустой `items`: отсутствие совпадений обрабатывается как пустой результат.

Затем передаю начало периода `2026-11-01` и конец `2026-09-01`. Сервер возвращает HTTP 422: обратный диапазон дат отвергается.

Также выполняю запрос с `search_mode=phrase`. Для одного слова это проверяет доступность режима, но не доказывает различие режимов: для этого нужен отдельный пример с несколькими словами и разным порядком токенов.

## Что было исправлено при проверке

При выполнении промежуточных запросов я обнаружил две ошибки Gateway. Корневой путь `/api/v1/schedule` приводил к перенаправлению на внутренний адрес сервиса. Кроме того, при передаче нескольких одноимённых параметров ID сохранялось только последнее значение. Я добавил обработку корневого пути сервиса и передачу всех значений query-параметров. Затем пересобрал Gateway и повторил весь прогон. Приведённый журнал получен после этих исправлений.

## Вывод и границы проверки

На текущем наборе я подтвердил получение защищённого отчёта через Gateway, прохождение страниц списка студентов, ограничение результата десятью записями, устойчивую сортировку при одинаковом проценте и совпадение с отдельным расчётом. Также проверил отсутствие доступа без JWT, пустую поисковую выдачу и неправильный диапазон дат.

Результат всех десяти студентов равен 0%: для найденных занятий нет отметок посещаемости. Поэтому этот прогон не доказывает правильность результатов 50% и 100%, различие многословного поиска и фразы, исключение отменённых и практических занятий на специально подготовленных контрпримерах, а также поведение при отказе зависимостей. Для полного покрытия нужны дополнительные контрольные данные; я не заявляю эти сценарии проверенными данным запуском.

Расчёт использует текущий состав групп, история переводов не восстанавливается. Поисковая проекция может отставать от основных данных. Эти ограничения следует учитывать при интерпретации результата.

## Как повторить проверку

На запущенной системе выполняю:

```bash
python tools/lab1/capture.py
```

Скрипт только читает предметные данные через Gateway, получает JWT и перезаписывает `docs/lab1/evidence.json` новым журналом. При расхождении независимого расчёта с отчётом выполнение завершается ошибкой. Он рассчитан на текущий демонстрационный набор и указанный период; это не универсальный генератор тестовых данных.
